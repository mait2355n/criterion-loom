# semantic-guard 1.1.0 運用手引

初めて使う場合は、[要求関係入力](#要求関係入力契約)又は[方向拘束入力](#方向拘束入力契約)から始め、
[解析の流れ](#解析の流れ)と[終了コード](#終了コードと監査状態)で結果を解釈する。
配布物と証拠を保守する場合は、[配布物の隔離検証](#配布物wheelの隔離検証)、
[正式な検証基準](#正式な検証基準と証拠更新)、[旧版比較](#旧版比較)、
[切替禁止条件](#切替禁止条件)を使う。

## 要求関係入力契約

現行の最小実装は、一件の構造化機能要求を対象にする。次の七項目を一行ずつ `label: value` で与える。

- `Purpose` / `目的`
- `User` / `利用者` / `主体`
- `Scenario` / `シナリオ` / `利用場面` / `場面`
- `Expected result` / `期待結果`
- `Acceptance criteria` / `受入基準`
- `Verification method` / `検証方法`
- `Evidence` / `証拠`

ラベルのない行、重複項目、複数記録、空項目は完全な構造化記録として扱わない。
この制約は、自由文から「欠落」や「満足」を断定しないための入力境界である。

CLI と MCP が一回に受け取る要求本文は UTF-8 で 262,144 バイト以下とする。
この実装は一件の構造化要求を対象にしており、複数文書を一件の要求として
結合入力してはならない。上限超過は解析前に拒否する。

次を UTF-8 の `requirement.txt` として保存すれば、公開 CLI の最小経路を再現できる。

```text
Purpose: 検索APIが検索結果を p95 500ms以内で返す
User: 検索API
Scenario: 検索APIが検索要求を処理して検索結果を返す
Expected result: 検索結果を p95 500ms以内で返す
Acceptance criteria: 検索応答時間 p95 500ms 以下
Verification method: 検索結果の検索応答時間を benchmark で測定する
Evidence: 検索結果の検索応答時間 benchmark report
```

```sh
uv run --locked semantic-guard audit-requirement --file requirement.txt
```

既定の `assurance` 経路で任意解析器を構成しない場合、上の入力では直接関係十件が
`presentation.met`、条件関係一件が `not_applicable` になる一方、必要な解析器の
実行範囲を満たさないため、主要状態は次の通りになる。

```json
{
  "audit_conclusion": {"outcome": "undetermined", "finality": "provisional"},
  "coverage": {"status": "partial"},
  "workflow_disposition": {
    "status": "warn",
    "acceptance_owner": "human_external_to_semantic_guard"
  }
}
```

これは主要項目だけの抜き出しであり、CLI は完全な
`semantic-guard-audit-result/v0` オブジェクトを返す。入力中の `benchmark report` は
提出された証拠記述であって、外部ファイルの存在又は測定内容を認証した事実ではない。
直接規則の一致だけで既定 `assurance` に必要な解析器の実行範囲や人間受理を補わない挙動を
示している。解析の流れと、明示選択の実験経路 `conditional` との違いは後述する。

## 方向拘束入力契約

`audit-direction-binding` / `audit_direction_binding_tool` は要求関係監査から独立し、
一件の方向を未指定のままにする表現と、そこへ直接結び付く方向指定だけを対象にする。
CLI は `--text`、UTF-8 `--file` 又は標準入力を受け、任意の `--context` は改行一つを挟んで
結合する。MCP は `text` と任意の `context` を受ける。結合後の入力は同じ
262,144 バイト上限を適用し、SHA-256 ハッシュ値で入力内容を固定する。監査対象となる操作は
`source_text` 内に書かれていなければならず、`context` だけに現れる別質問や例を主判定の対象にはしない。

```sh
uv run --locked semantic-guard audit-direction-binding \
  --text '体重が重い順に並べたとき、Cの次に体重が重い人は誰か。' \
  --context '候補集合は現在の表だけを使う。' \
  --morphology sudachi
uv run --locked semantic-guard schema direction-binding-audit
```

形態素解析は `signal_only` で、数値の対応付けは補助証拠に限る。`morphology=none`、
部分被覆、失敗又は契約不整合を方向拘束の成立へ置き換えない。方向監査は
`semantic-guard-direction-binding-audit/v1` を返し、既存 `audit-result/v0` へ項目を追加しない。

## 配布物（wheel）の隔離検証

正式な基準となるリポジトリのルートを作業ディレクトリとし、信頼済みのローカル
作業木から `wheel` を一個だけ構築して、隔離仮想環境へ導入した配布実体を検証する。
検証器は隣接する偽の `schemas/` と `validation/` を置いた上で、配布物内の24スキーマ、
CLIコマンド四件、MCPツール四件、ライフサイクル候補10件、工学規則候補11件とそのスキーマ、
空オブジェクトを拒む運用成果スキーマを再現する。

```sh
uv build --out-dir dist .
uv run --locked python scripts/verify_packaged_contracts.py \
  --wheel dist/semantic_guard-1.1.0-*.whl \
  --sdist dist/semantic_guard-1.1.0.tar.gz \
  --timeout-seconds 180
```

`dist/` には対象 `wheel` 一個だけを置く。標準出力は機械可読 JSON 一個で、
`status=pass` の時だけ終了コード `0`、入力、導入、資源上限、経路又は契約検証の不成立は
非零となる。検証器は外部の Python、監査プログラム又は資源パスを引数で選ばせず、
`wheel` ファイルの容量、展開量、全体の制限時間、子プロセスの CPU 使用量、出力量、生成ファイル量及び
ファイル記述子数を制限する。Darwin では有限 `RLIMIT_AS` を受理しないため、
アドレス空間上限だけは適用せず、結果の制限事項に明記する。

これは未知の `wheel` を安全に実行できる隔離環境ではない。`wheel` の読み込み自体が
コードを実行するため、運用者が信頼するローカル構築物だけを対象にする。依存解決には
バイナリ配布物だけを許すが、配布索引、通信及びその時点の互換依存版には依存する。
成功しても、同梱資源とローカル契約の再現を示すだけで、実地妥当性、運用適格性、
外部資料の真正性、安全性の認証又は人間受理にはならない。

1.1.0 の選択配布物、登録済み方向例、GitHub 統合及び CI に関する 2026-08-23 の
観測値は、[実装状態](implementation-status.md)と日付付きの
[統合証拠](audits/direction-binding-integration-2026-08-23.md)へ分離する。それらは
記録対象の証拠であり、この運用コマンドや別の構築物の適合を自動的に保証しない。

## 解析の流れ

```text
入力境界
  → 義務別直接仮判定
  → 残った危険を独立に確認
  → 必要時のみ形態素解析
  → 依存構造候補
  → 版付き決定論的再検査
  → assurance / shadow_all 経路で明示的に渡された LLM 候補（conditional は未解決時）
  → 義務別再集約
  → 人間に判断を求めるための材料
```

既定の `assurance` は直接規則が通っても形態素・依存構造解析を実際に実行し、
必須解析器が無い又は失敗した場合は `pass` にしない。`conditional` は残余危険
又は未解決義務がある場合だけ解析器を起動する、効率化のための候補経路であり、実務資料による
見逃し評価が終わるまでは明示選択の実験経路とする。

`shadow_all` では解析器を観測用に全件実行するが、その信号、競合、解釈を最終的な判定へ
混入させない。観測専用の結果を採用するには、別の版付き規則と適合試験が要る。

## 終了コードと監査状態

CLI は、入力解釈と監査実行が完了した場合の機械可読 JSON だけを標準出力へ書く。利用法違反、UTF-8 復号、入力上限、候補データの読込みなど、監査開始前の診断は標準誤出力へ書き、終了コード `2` とする。予期しない処理異常による非零終了を監査上の `block` と読み替えてはならない。有効な公開 JSON が無ければ、監査結果そのものが得られていない。

CLI の終了コード `0` は JSON 生成と契約検証が成功したことを示す。監査結論は `workflow_disposition.status` を読む。`warn` や `block` を処理異常と混同してはならず、逆に終了コード `0` を監査通過とみなしてもならない。

自動処理で監査状態も終了コードへ対応付ける場合は `--fail-on warn` 又は
`--fail-on block` を明示する。閾値に達しても JSON は完全な形で標準出力へ出し、
その後に終了コード `3` を返す。旧版比較を必須にする `--require-legacy` が失敗した
場合は終了コード `4` を優先する。既定 `--fail-on never` は従来どおり、終了コードと
監査結論を分離する。従って `0 / 2 / 3 / 4` はそれぞれ、JSON 出力と契約検証の成功、
利用方法の誤り又は無効な入力、明示された監査状態の閾値、必須とした旧版観測の不成立を表す。

`pass` は「現行の版付き監査規則が止めていない」という対応付けでしかない。受理、
差戻し、保留、延期、棄却は外部の人間判断に残る。

## 解析器障害

- `conditional` で必要になった解析器が未構成、失敗、部分被覆なら `pass` にはならない。
- `shadow_all` の未構成解析器は観測として残るが、実効判定を変えない。
- Sudachi と GiNZA は任意依存であり、導入していない環境では障害が明示される。
- 方向拘束監査では Sudachi だけを選択できる。未構成、部分被覆、失敗又は能力・
  分割モードの不整合は `primary_rule_evaluation.state=indeterminate|invalid` として残り、
  形態素だけから方向を導出しない。
- `partial` な解析器出力は全てを成功扱いにも全てを廃棄にもせず、充足能力だけを
  候補専用経路で使う。係り受け結果の対応付けは `dependency`、条件作用域の限定導出は
  `dependency` と `scope` の充足を要する。欠落能力がある実行は、候補を使えても
  完全被覆又は `pass` にはならない。
- GiNZA の未加工の候補は `dependency:*` 名前空間に留める。そのうち主語、目的語、原文上の
  位置と対応付けられた条件の作用域だけを、版付き規則で `performs`、`acts_on`、`triggered_by` の意味関係
  候補へ対応付ける。これは差分検知用の候補であり、正しさを支持する証拠ではない。

## LLM 候補一式

主な呼出元はコーディングエージェントなので、特定の外部モデル API を監査器内部へ
固定しない。呼出元は `semantic-guard-llm-candidates/v0` の項目を限定した JSON データを生成し、
CLI では `--llm-candidates FILE`、MCP では `llm_candidate_bundle` として渡す。

このデータには原文の SHA-256 ハッシュ値、モデル識別子と版、指示規約識別子と版、候補ごとの
関係種別、開始位置と終了位置、解釈識別子、根拠を必須とする。原文ハッシュ値の不一致、不正範囲、
未知項目は失敗として記録する。モデル名は呼出元による来歴の申告であって、認証済みの同一性ではない。
LLM 候補は常に `candidate_only` であり、支持、保留適用、保留解除はできない。候補データを明示的に渡した
`assurance` では先行段階が仮通過していても候補を観測する。LLM が返した反条件・
作用域候補は、版付き残余危険方針によって保留材料へ対応付け、黙って捨てない。

```sh
uv run --locked semantic-guard schema llm-candidate-input
```

## 安全で責任ある運用の候補基準

実資料を外部 LLM 又は解析器へ送る権限は、この一連の監査機能を実装しただけでは生じない。
`verification.cross.secure-and-responsible-operation` は、資料分類、同意又は権限、最小化、
秘密・個人情報、外部送信、保持・削除、敵対入力、依存・モデル・辞書の来歴、最小権限、
資源枯渇、事故証拠と復旧を、項目を限定した検証範囲へ入れる候補基準である。
`secure-operation/v1` のローカル補助契約は、与えられた情報の流れ・範囲・保持・削除・
採択/廃止・再起動・証拠種別・資源上限記録の内部整合だけを検査する。実署名、
外部本人性、信頼時刻、外部台帳、実配備観測及び独立した運用適格性評価は無く、人間採択も
未了である。そのため、正式な基準上の状態を「実装済み」「検証済み」と推測してはならない。
セキュリティ検査器や適合性認証を名乗るものではない。

人間が用途、資料、送信先、保持、権限、事故・残危険方針を採用する前に、呼出元は
非公開資料を外部提供者へ送ってはならない。採用後も、外部呼出、作業実行、危険受容は
呼出側又は作業管理側の責務であり、`semantic-guard` は不足と証拠を監査するだけである。

候補基準を採用しないだけでは、この未解決事項は消えない。解消には二つの経路がある。
採用した配備プロファイルに、不足時には安全側で停止する制御と独立した敵対的検証の証拠を
備えるか、実資料・保護情報、外部提供者、特権操作、永続運用を除外する版付きの非適用境界と
再評価の開始条件を人間が受理し、対象目録、構成、情報の流れ、外部提供者、権限、保存経路を
参照位置付きで観測して、実際に境界内であることを示す。紙上の宣言だけでは後者にならない。境界を越えた時点で、
実装・独立査読義務は再び有効になる。

## 正式な検証基準と証拠更新

`validation/verification-source.json` は、検証要求、証拠関係、独立状態軸、再検証条件、
未決定事項を保持する正式な検証基準である。`verification-matrix.md` は人間向け表示、
日付付き検証 JSON は実行時点の観測であり、三者を同じ物として更新しない。

更新順は次で固定する。

1. 原点要求、憲法、公開契約又は証拠対象が変わった場合、正式な検証基準中の上流版又はハッシュ値を先に更新する。
2. 過去の日付付き観測を現状に合わせて書き換えない。再実行したなら新しい観測を追加し、取得方法、証拠ファイルのハッシュ値、試験対象の記録位置と項目を限定した目録又は全対象のハッシュ値、環境、実行コマンド又は未加工ログの記録位置、結果、限界を記録する。
3. 証拠観測を `evidence_observations` へ正規化し、証拠が命題又は状態軸へ及ぼす作用を `evidence_effects` に記録する。

   - 各作用は、対象項目、証拠、`supports / refutes / challenges / contextualizes`、`claim_dimensions`、限定命題、宣言済みの観測位置（`locator`）、限界を持つ。
   - `supports / contextualizes` は項目の `evidence_refs`、`refutes / challenges` は `counterevidence_refs` と集合を一致させる。
   - `contextualizes` は命題形成の文脈であって、実装・検証・妥当性・保証を支持する証拠ではない。`lifecycle_surfaces` で一部だけを対象とする支持も、親項目の全工程被覆を満たさない。
   - `missing / failed / invalid / refuted_in_context` には、同じ状態軸への負の作用を必須とする。同じ軸への支持作用もあるなら `challenge=conflict` を要する。負の証拠が無いときは欠落を断定せず、`not_assessed` に留める。
   - 反証・疑義は保証次元を必ず含める。試験名や予定だけを実行証拠にせず、同じ証拠ファイル内の別位置を観測位置の代わりに使わない。
4. 実装、検証、妥当性確認、限定的保証、鮮度、人間受理を各々更新する。一軸の成功から他軸を推測しない。
5. `terminal` は、現在の対象へ結び付いた `current` 証拠、限定範囲を満たす被覆、未解決の疑義が無いことを要する。

   - `refuted` 又は `challenge=open/conflict` には、参照位置を示した型付きの作用を必須とする。`refuted` には少なくとも一つの `refutes` が要る。
   - `challenges` は `challenge=open/conflict` を、`refutes` は `outcome=refuted` を要する。ただし反証命題と被覆が閉じていれば、`terminal refuted / challenge=none` は許される。
   - 単なる不確実性を疑義と呼ばない。記録位置は、参照証拠に宣言された観測位置だけを使う。

6. 証拠ファイル自体のハッシュ値だけを、試験対象の時点記録に結び付いた証拠とみなさない。

   - 全 `subject_locators` がハッシュ値で覆われない証拠は `current` にしない。現在の対象へ結び付かない証拠は `stale` 又は `unbound` とする。
   - `test_execution / bound` には、SHA-256 で結び付けた `semantic-guard-evidence-subject-manifest/v0`、`closed_world=true`、目録と一致する全対象ハッシュ値、証拠報告及び目録自身とは異なる少なくとも一つの試験対象、環境、実行コマンド又は未加工ログの記録位置を必須とする。
   - 報告 JSON 自身だけを対象範囲にして `bound` へ昇格してはならない。項目状態を `current` にするなら、その項目が参照する全証拠も `current / bound` でなければならない。
   - 失効、変更の影響、再評価条件が未定なら、その欠落自体を未解決として残す。
7. `independently_observed / signed / formally_verified` を名乗る観測は、観測者と独立性根拠、署名・信頼根・証明、又は形式モデル・検証器・検証結果の該当項目を満たし、根拠成果物の記録位置が実在しなければならない。なお公開来歴契約にはこの拘束がまだ無く、保証プロファイルの採用と共に未解決である。
8. 未解決事項が各項目の状態を不当に引き上げないようにする。

   - `blocks_claim` は対象項目の `satisfied` を禁止し、`blocks_claim / partially_blocks_claim` は `terminal satisfied` を禁止する。反証命題と被覆が閉じた `terminal refuted` は妨げない。表示用の参照も構成項目へ展開する。
   - 各解消責務には、安定した `obligation_id`、権限級の根拠、前提責務への参照を付ける。`resolution_paths` には、分岐の開始条件、同じ未解決事項で必要な責務、完了証拠の条件を列挙する。
   - 全責務を少なくとも一つの経路で覆い、同じ未解決事項内の前提を選択経路から落としてはならない。
   - `resolution_summary` は正式な規則ではない要約であり、経路の選択、優先順位、割当は人間又は外部の作業管理機構が決める。
   - 現版の開始条件は自由文である。検証器は、経路へ到達できること、相互排他性、網羅性、選択又は完了を証明しない。型付きの選択・完了評価記録を実装するまでは、自由文の条件だけを根拠に未解決事項を削除してはならない。
9. 正式な検証基準を先に直し、`verification-source.generated.md` を決定論的に再生成する。生成物へ直接追記してはならない。`verification-matrix.md` は判断補助の編纂文書であり、正式な検証基準の完全表示とは扱わない。
10. 生成表示の完全一致と、正式な検証基準のスキーマ、全参照が解決できること、ローカルパス・ハッシュ値、基準自体のハッシュ値を内部検証器で確認する。

```sh
uv run --locked python scripts/render_verification_projection.py
uv run --locked python scripts/render_verification_projection.py --check
uv run --locked python scripts/validate_verification_source.py
```

生成表示は、正式な検証基準にある全てのオブジェクト、配列、単一値を JSON Pointer 付きで一度ずつ列挙する。
内部検証器は生成文字列の完全一致まで検査するので、値の脱落又は手編集によるずれは
検出できる。ただし、編纂文書 `verification-matrix.md` の説明が正式な検証基準と同じ意味か、
又は生成表示の値が実世界で真かを証明するものではない。

この検証器の成功はローカルな整合性の観測に限られる。実務性能、行為真正性、人間受理までは
立証しない。結果 JSON は検証器のハッシュ値、実行時刻、Python・`jsonschema` 版、
ソースコード・スキーマ・共通スキーマ・生成表示のハッシュ値を含む。検査開始時と終了時にも
追跡対象のハッシュ値を比較するが、信頼済みの時点記録、時刻証明又は敵対的な変更や復元競合への
耐性にはならない。永続証拠として用いるなら、この出力自体と対象環境を新しい日付付き観測へ
固定し、現ソースコードの自己申告へ循環させない。

内部検証器の結果契約は
[`verification-validation-result.schema.json`](../validation/verification-validation-result.schema.json)
である。公開する入出力は次の通り。

- 引数の解釈まで成立した検証実行は、標準出力へ `schema_version / status / subject / execution / checks / counts / errors / limitations` を持つ JSON 一個を出す。
- `status=error` の `errors[]` は `code / location / message` を持つ。ソースの配列項目がスキーマと異なる型でも、この JSON の失敗時形式を失わない。
- 検証成功は終了コード `0`、スキーマ、参照、パス、ハッシュ値又は生成表示の不成立は `1`、未知の引数などコマンドラインの利用法違反は標準誤出力と `2` である。
- 入力ソース、スキーマ、生成表示はリポジトリ内で解決できなければならない。外部パスは読まず、`path_outside_repository` とする。
- 人間受理を `pending` 以外へ変える場合、判断時刻は登録済み証拠より後でなければならず、`decision_record_ref` はリポジトリ内の実在記録を指さなければならない。

正式な検証基準は、欠落、競合、証拠不足、再検証条件を明らかにできるが、実装の優先度、作業の委譲、実行権限、切替、危険の受容までは決めない。管制は外部の呼出側又は `resource-control-plane` が担い、最終的な `accept / request_revision / defer` は人間が決める。

## 旧版比較

旧版は、運用者が所有する外部ルートにある `vnext/migration/legacy-baseline-2026-07-17.json`
の、項目を限定したファイルハッシュ値集合を照合してから別プロセスで実行する。現在の取得候補は
155ファイルを照合するが、`capture_authority=pending_human_acceptance` であり、人間採択済みの
正解基準ではない。リポジトリ内の `legacy/semantic-guard-v0.1.0/` は、公開用に修復した
旧版資料及び実行ソースの保存場所であり、元のバイト列を示す正式な参照先は注釈付きタグ `v0.1.0` と
コミット `e0a3dd39f17385b66f6361ade25eb44bed6e1ab3` にある。この保存ディレクトリ自体は、
必要な実行体と同じ相対配置を備えた信頼ルートではない。2026-07-15及び2026-07-16の
目録は歴史的観測として残すが、通常実行時の信頼の起点には使わない。ハッシュ値がずれた場合、
既定では比較を行わない。

MCP ツール `shadow_compare_legacy_tool` による旧版比較は既定で無効である。CLI の対応するサブコマンドは
`shadow-compare` である。いずれも呼出側から実行ファイル、変換器、目録、
ソースルートを指定させない。サーバー運用者が必要性と対象を確認した場合だけ、
MCP サーバーの実行環境に次を設定する。

```sh
SEMANTIC_GUARD_ENABLE_LEGACY_SHADOW=1
SEMANTIC_GUARD_LEGACY_ROOT=/absolute/operator-owned/legacy-root
```

ルートは絶対パスで、`.venv/bin/python`、固定位置の
`vnext/scripts/legacy_request_adapter.py`、
`vnext/migration/legacy-baseline-2026-07-17.json` を含まなければならない。変換器と目録が
ルート外へ解決される場合は拒否する。目録自体のハッシュ値も MCP サーバー側に固定する。
空、構造不正、空ハッシュ値一覧、非正規相対パス、不正な SHA-256、必須旧版ソース又は
変換器の欠落、固定した対象範囲とハッシュ値一覧の不一致を持つ目録は `allow_baseline_drift` の
有無にかかわらず実行しない。新しい信頼根の採取には `capture_legacy_baseline.py` の
明示確認フラグが必要であり、生成物自体も人間の受理前は信頼済みとは扱わない。

旧版変換器は、選択した目録に固定されたルート内パスだけを実行する。Python 実行体の
SHA-256 も照合し、環境変数は限定規約へ正規化する。実行後に基準状態を再照合し、途中の
ずれは結果を無効化する。標準出力は旧版 `audit-result` スキーマと
`phase=audit_request` に適合した場合だけ `completed` とし、入力・文脈のハッシュ値、
プロファイル、論理追跡方式、制限時間、出力ハッシュ値を実行観測へ残す。
`--require-legacy` は実行完了だけでなく、基準状態との一致、変換器の固定、出力スキーマ適合を
要する。CLI の目録・変換器の明示差替えはローカル診断用であり、MCP の通常基準線と
同一視してはならない。

採取器は、観測していない試験結果を目録に記録しない。試験・診断・標本評価の実観測は
`validation/` の別記録に残す。実行体のハッシュ値とロックファイルは通常のずれを検出するが、
OS、動的ライブラリ、ホスト、署名済み来歴又は悪意ある実行環境の真正性までは立証しない。

差分は少なくとも観測差分、方向、評価、根拠種別を分ける。新旧不一致だけで v1 の後退又は
改善を断定しない。裁定根拠は憲法不変条件、適合例、変形不変条件、裁定済み実務例、
運用証拠のいずれかでなければならない。

## 切替禁止条件

- 導入対象を、[実装状態](implementation-status.md)の「1.1.0 GitHub統合観測」が示す
  マージコミット `a77c3cbdc69295572e90333e2a6e9da690fbbb6d` 又はそれを祖先に持つ明示コミットへ
