# 試作群の原点要求

作成日: 2026-06-30
更新日: 2026-08-24

## 目的

この文書は、`docs/prototypes/` 配下の配置にかかわらず、Criterion Loom / `semantic-guard` の現在の目的を定める正式な基準である。この配置によって本書の状態が候補へ下がることはない一方、個別の試作の実装又は採択を意味しない。

本書は、複数の試作（`prototype`）を評価する際に、保持対象、評価対象及び棄却条件を判断するための要求を定める。

## 原点要求

### OR-01 — 工程横断の体系監査

Criterion Loom は、AI エージェントが関与する開発工程の依頼、探索前の問い、要求、決定状態、計画、行為、実現方針、差分、検証、完了主張を、要求工学、計画工学、ソフトウェア／システム工学その他の明示された体系化された専門知識（以下「体系知」）に照らして監査する。

監査は、正しさを主張する根拠とその限界を明らかにし、不足、未決定、仮説、推測、意味のずれ、矛盾、難点、危険、証拠不足を構造化された結果として外部化する。

### OR-02 — AI エージェント行為の限定的立証

Criterion Loom は、AI エージェントの各工程行為について、対象命題ごとに、記録された要求、前提、規則、権限、主体、観測者、実行、入出力、成果物、検証証拠、信頼条件の範囲内で、何が支持され、何が反証され、何が未証明または矛盾状態にあるかを示す限定的な立証を構成し、監査可能にする。

この責務は、記述が整っていることと、行為が実際に起きたことを別の命題として扱う。

### OR-03 — 修正と人間判断への接続

監査結果と限定的立証は、AI エージェントの再計画、再実装、変更説明、検証、完了報告の修正へ戻せる材料であり、同時に人間が最終的に `accept`、`request_revision`、`defer` を判断するための材料である。

求めるのは、判定機構が正しさを自動承認することではない。判断の根拠、未決定、証拠、反証条件、未証明範囲、限界を見える場所へ出し、後続の修正と人間判断へ接続できる状態を保つことである。

## 正しさと限定的立証の意味

本書でいう「正しさを担保する」とは、対象の正しさを無条件に確定することではない。対象命題、適用範囲、信頼前提、規則、観測、証拠、反証条件、未観測範囲、残余危険を追跡可能にし、何がどこまで支持されるかを再検査可能にすることを指す。

「限定的な立証」とは、対象命題と必要証拠が明示され、使用した証拠と導出を再現でき、証拠不足、反証、矛盾、被覆不足がある場合は未証明として残る保証主張を指す。

形式的証明、暗号的真正性、実行主体の本人性、改竄不能性を主張できるのは、それぞれに必要な形式モデル、検証器、信頼根、署名、透明性記録その他の機構が実装され、その機構自体の前提と限界が明示されている場合に限る。

## 現在の実装状態

`OR-01`、`OR-02`、`OR-03` は到達すべき要求であり、現実装がすでに全項目を実現したという完成主張ではない。

正式版1.1.0は、単一の構造化機能要求を義務へ分け、直接規則、未解決事項の再集約、形態素解析の信号、係り受けなどの候補、呼出元が提出するLLM候補を、権限を分けたまま検査する要求関係監査に加え、同一対象・同一操作で方向を未指定のままにする表現へ、方向を限定する表現が直接結び付いているかを検査する独立した方向拘束監査を公開面に持つ。公開CLIは `audit-requirement`、`audit-direction-binding`、`shadow-compare`、`schema` の四コマンド、MCPはそれぞれに対応する四ツール、値や項目を限定したスキーマ登録簿は24件である。要求関係監査では形態素解析は `signal_only`、依存構造解析とLLMは `candidate_only` が上限である。方向拘束監査でも形態素解析は `signal_only`、数値の抜き出しは補助証拠に限り、いずれも未加工の出力だけでは支持、人間受理又は方向選択を成立させない。

要求工程以外のライフサイクル方針（`profile`）、行為証拠、状態評価、修復、実地評価、安全運用、運用適格性、移行には版付き候補又は補助契約（`sidecar`）があるが、共通の公開処理経路（`workflow`）、人間採択、実地証拠、外部真正性は未成立である。従って `OR-01`、`OR-02`、`OR-03` の全工程達成済みとはしない。

旧0.1.0が持っていた文書、要求、計画、差分、完了、規約、査読、受理材料の局所監査は、`legacy/semantic-guard-v0.1.0/` に公開用修復済みの歴史的な保管資料（`archive`）として保存する。元のバイト単位の内容に対する権威は、注釈付きタグ `v0.1.0`、コミット `e0a3dd39f17385b66f6361ade25eb44bed6e1ab3` のGit上の基点に残り、現在のディレクトリは元の時点記録（`snapshot`）ではない。これらは未移植工程の互換導線であって、v1の正式な基準へ透過的に統合された機能でも、正しさの基準（`oracle`）でもない。

正式な基準への昇格境界は `docs/canonical-promotion-decision.md`、移行は `docs/migration-v0.1.0-to-v1.0.0.md`、1.1.0の実装状態は `docs/implementation-status.md`、方向拘束統合証拠は `docs/audits/direction-binding-integration-2026-08-23.md` に記録する。要求上の語義、局所契約適合、実務妥当性、人間採択を混同しない。

## なぜ必要か

AI エージェントが生成する計画、完了報告及び自己点検では、事実、仮説、未決定事項及び確認済み証拠の区別が会話文脈にだけ残り、成果物から検査できない場合がある。

Criterion Loom の価値は、この区別と判断材料を監査可能な成果物として外部化する点にある。高性能な自然言語判定器に見せることではない。実装、文書、試験、監査、受入判断を続けるために、作業の意味と証拠を扱える形へ戻すことにある。

## 実現したい状態

実現したい状態は次である。

AI エージェントの作業について、要求、計画、行為、変更、検証、完了主張のどこに不足や不確実性があるかを、体系知へ追跡できる規則、証拠、適用しない条件（反適用条件）、信頼前提、限界、人間判断点つきで説明できる。さらに行為に関する対象命題を、支持、反証、未証明、矛盾へ分け、その結果を次の修正行動へ戻せる。

成果物名やコマンド数ではなく、この状態が実現されているかを見る。

## 対象読者と使い方

- CodexなどのAIエージェント: 監査結果を受け取り、依頼解釈、計画、差分説明、検証、完了報告を修正する。
- 人間の受入判断者: 監査結果、実行証拠、残危険を見て、受理、差戻し、保留を判断する。
- 保守者: 規則、試験用データ、評価用資料群、スキーマ、外部証拠連携が原点要求から逸れていないかを確認する。

派生作業では次の順に記録を確認する。

1. 試作の開始前に、この文書を確認する。
2. 試作計画書に `origin_trace` を記録する。
3. 試作計画書を監査し、原点要求へ追跡できる場合だけ実装へ進む。
4. 試作の採用、差戻し、保留、棄却は、人間判断材料として扱う。

正式版v1で一つの機能要求を監査する例:

```sh
uv run --locked semantic-guard audit-requirement \
  --text '監査結果は、未解決義務と根拠範囲を保持しなければならない。'
```

この原点文書全体に対する旧 `audit-request --kind document` が必要なら、公開用修復済みの旧版保管資料を明示して実行する。これはv1監査ではなく、元の0.1.0のバイト単位の時点記録を再現するものでもない。

```sh
cd legacy/semantic-guard-v0.1.0
uv run --locked semantic-guard audit-request \
  --kind document --file ../../docs/prototypes/origin-requirement.md
```

## 非目標

- 人間の最終判断を代替すること。
- LLM査読者の出力を承認、棄却、警告解除の根拠として単独採用すること。
- 試験用データの通過率を、任意文書に対する一般精度として主張すること。
- セキュリティ検査器、リリース判定機能、法務判定器、品質部門判定器を名乗ること。
- 要求工学、計画工学、ソフトウェア／システム工学等の全体系または全規格条項を実装したと主張し、規格適合審査や専門家判断を代替すること。
- 記録されていない行為、観測範囲外の事実、隠れた行為の不存在を証明したと扱うこと。
- 自己申告、字句一致、説明文の完全性だけを、行為発生、権限、成果物生成、検証成功の証拠として採用すること。
- 必要な信頼根や検証機構なしに、形式証明、真正性、本人性、因果性、改竄不能性を主張すること。
- `semantic-guard` が AI エージェントの実行管制、優先度、権限付与、永続台帳、最終受理を担うこと。
- すべての試作を一つの巨大機能へ混ぜること。
- 公開CLI、MCP、スキーマの契約を、試作の都合で暗黙に変えること。

## 契約境界

この文書は、試作群の原点要求であり、新しい公開CLI、MCPツール、API、スキーマ、永続記録形式を定義しない。

正式版v1の正式な項目、型、列挙値、条件制約は `schemas/audit-result.schema.json` と、そこから参照されるスキーマを基準とする。旧0.1.0の `phase`、`status`、`score`、`findings`、`missing`、`next_actions`、`details` という共通形は旧版保管資料の契約であり、v1の値や項目を限定した義務結果へ読み替えない。

この文書自身が対象とするリポジトリ方針の境界は次の通りである。

- `schema_version`: `prototype-origin-requirement/v3`。
- `repository_id`: `semantic-guard`。
- `public_surfaces`: 文書のみ（`documentation only`）。
- `commands`: 正式版1.1.0の公開CLIは `audit-requirement`、`audit-direction-binding`、`shadow-compare`、`schema` の四コマンドである。原点文書全体の旧文書監査は `legacy/semantic-guard-v0.1.0/` 内の `audit-request --kind document` を明示的に使う。
- `output_shapes`: 新しい出力形式なし（`no new output shape`）。
- `exceptions`: 試作固有のスキーマ、CLI、MCP、API、記録形式は、個別の試作計画書又は別スキーマで定義する。
- `internal_scope`: 試作の内部実装、検出器設計、試験用データ追加、評価用資料群の採点は個別の試作側で扱う。
- `non_goals`: 公開契約の定義、旧版契約のv1への暗黙併合、リリース判定機能、人間判断の代替。

試作が新しい構造化出力を持つ場合は、別文書又はスキーマで次を定義する。

- `schema_version` 又はスキーマの所在。
- 名前付き項目と値の型又は列挙値。
- 成功時の形: `status`、`payload` 又は `result`、`metadata` 又は `details`。
- 失敗時の形: `error.code`、`error.message`、`error.details`、`next_actions`。
- CLIを増やす場合の `stdout`、`stderr`、終了コード。
- 永続記録を作る場合の時区付きISO 8601時刻、証拠の出所、事実（`fact`）／推論（`inference`）／仮説（`hypothesis`）／判断待ち（`pending decision`）の区別。
- 少ない情報で作業を再開するための項目: `context`、`current_state`、`action`、`detail_refs`。

## 不変条件

すべての試作は、次の不変条件を守る。

1. 監査結果は中間材料であり、最終判断ではない。
2. 人間の最終判断境界を残す。
3. LLMは補助材料に限る。決定論的な規則、構造化証拠、実行証拠を優先する。
4. `pass` は「現行規則では止めない」であり、実務上の受入ではない。
5. 局所の試験用データと実地の評価用資料群を分ける。回帰検出と一般性能評価を混同しない。
6. 試作は原則として補助契約として作る。本体中核へ入れるのは昇格条件を満たした後に限る。
7. 各試作は、この原点要求のどの部分を強めるかを明記する。
8. 複数の試作は別案として保つ。共通核だけを上位で束ねる。
9. 字句の存在と、肯定命題の成立を同一視しない。
10. 記述物の完全性監査と、実行行為の立証を別の命題として扱う。
11. 支持される命題は、対象、範囲、証拠、信頼前提、反証条件、被覆、未証明範囲を持つ。
12. 証拠不足、観測不能、矛盾、ハッシュ値不一致を、暗黙の成功又は `pass` へ昇格させない。
13. 自己申告、ツール出力、ファイルシステム観測、CI結果、人間の証言、署名付き証明書は、同一の信頼強度として扱わない。
14. `semantic-guard` は監査と立証検査を担当し、実行管制、優先度、永続台帳、次行動は `resource-control-plane` 側が担い、人間の最終受理は人間側へ残す。

## 試作計画書に必要な項目

各試作計画書は、最低限次を記録する。

- `prototype_id`: 安定した識別子。
- `hypothesis`: 何を確かめる試作か。
- `origin_trace`: `OR-01`、`OR-02`、`OR-03`、不変条件、非目標のどれに接続するか。
- `input_output`: 入力、出力、保存形式、公開契約を変えるか。
- `llm_dependency`: LLM なしで成否を測れる部分と、LLM を使う場合の補助範囲。
- `evidence_plan`: 価値、判定品質、妥当性、限界を点検する証拠。
- `acceptance_criteria`: 何が見えれば成功か。
- `rejection_conditions`: 何が起きたら棄却または差戻しか。
- `hollow_success_conditions`: 物はできたが本質的には失敗している条件。
- `promotion_criteria`: 補助契約から本体へ昇格してよい条件。
- `rollback_or_disposal`: 捨てる、止める、戻す方法。

## 受入条件

この原点要求に沿った試作群は、次を満たす。

- 各試作が `origin_trace` を持つ。
- 各試作が少なくとも一つ、LLMのモデル性能に依存しない評価証拠を持つ。
- 規則、スキーマ、試験用データ、評価用資料群、外部証拠、追跡、受入資料一式のどれを改善するかが分かる。
- 価値、判定品質、妥当性、限界を別々に述べる。
- 局所較正結果と任意文書への一般化を分ける。
- 人間判断境界を侵さない。
- 本体契約を変える場合は、別計画、規約監査、試験、移行説明を要求する。
- 各試作が `OR-01`、`OR-02`、`OR-03` のどれを強めるかを安定した識別子で追跡できる。
- 体系知を用いる規則は、根拠、適用条件、反適用条件、必要証拠、限界を持ち、規格適合そのものとは区別される。
- 行為に関する主張は、対象命題、必要証拠、信頼前提、反証条件、被覆、未証明範囲を明示する。
- 記述物の完全性、行為発生、手続適合、成果物との関係、検証結果を別々の命題として扱う。
- 否定、引用、例示、条件、歴史記述中の字句を、独立した肯定命題または行為証拠へ自動昇格させない。
- 証拠不足、反証、矛盾、観測不能、ハッシュ値不一致がある場合、支持又は成功へ昇格せず未証明範囲を残す。
- 同じ入力証拠、規則版、ツール版から立証導出を再検査できる。

## 見かけ上の成功条件

次の状態は、成果物が存在しても失敗である。

- 試作が増えたが、原点要求への接続が説明できない。
- 試験用データが通ったことを、一般性能の証明として扱っている場合。
- LLM査読者の判断を、最終承認又は警告解除として扱っている。
- 入出力契約、スキーマ、CLIの変更が、試作という名目で暗黙に混ざっている。
- 監査結果が人間向け静的報告で止まり、AI エージェントの修正行動へ戻らない。
- 複数の試作が混ざり、一つずつ採否判断できない。
- 体系知の名称を並べたが、規則根拠、適用条件、反適用条件、必要証拠を追跡できない。
- 行為記録を増やしたが、主体、権限、観測者、時刻、入出力、成果物のハッシュ値、反証条件がない。
- 意味を誤って抜き出した事実へ署名し、暗号学的には堅牢でも意味が誤った証明を作る。
- 主張の分類と信頼前提を定めず、「証明可能」という語だけを追加する。

## 候補となる試作群

この一覧は候補であり、要求ではない。

| 試作 | 強める対象 | LLMに依存しない証拠 |
| --- | --- | --- |
| `rule-trace` | 規則、根拠、適用条件、反適用条件、非発火理由 | 規則検出器の対応付け、導出用の試験データ |
| `corpus-calibration` | 実例に対する警告品質、過警告、警告漏れ | 採点済み実地資料群の評価量 |
| `external-evidence` | 試験、走査、被覆、代表実行の証拠連携 | ツール出力スキーマと簡易動作試験 |
| `action-evidence-envelope` | 行為命題、主体、権限、観測、入出力、成果物関係、信頼前提、反証条件 | 行為証拠一式の決定論的検証と敵対的な試験データ |
| `concept-drift-guard` | 原点要求からの逸脱検出 | 文書監査用の試験データと禁止主張 |
| `revision-loop-repair` | 監査結果から再計画、再実装、完了報告修正への接続 | `rule_id` と修復様式の対応被覆 |

## 採否規則

- `adopt`: 原点要求へ追跡でき、証拠があり、非目標を侵さず、保守可能である。
- `revise`: 価値はあるが、証拠、境界、反適用条件、評価方法が不足している。
- `defer`: 価値はあるが、現在の試作群の中核ではない。
- `reject`: 人間判断代替、過大主張、巨大統合、LLM 依存承認、契約破壊につながる。

## 判断主体

個別の試作の採否と優先順位、評価用資料群の規模と採点語彙、補助成果物の保存場所と命名規則、行為主張の分類、信頼・脅威モデル、立証義務及び外部証拠の真正性確認方法は、本書だけでは決めない。版付きの判断記録と人間の受理に残す。

## 派生作業の開始条件

本書から試作又は派生実装を開始する場合、対象の試作計画書が安定した `prototype_id`、`origin_trace`、非目標、`evidence_plan`、`acceptance_criteria`、`rejection_conditions` 及び `rollback_or_disposal` を持ち、本書への追跡を査読可能に示すことが開始条件である。この条件を満たさない作業は、本書に由来する試作として実装段階へ進めない。
