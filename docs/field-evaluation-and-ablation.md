# Field evaluation and route ablation

## 結論

`field-evaluation/v0` は、同一の保留標本に対して `direct_only`、`morphology`、`dependency`、`llm` の四経路を走らせ、直接規則の後へ各解析段階を足す増分価値と誤りを比較する内部試作契約である。

単なる正答率比較ではない。人間が先に採択した母集団、用途、層、誤り費用、閾値、最低標本数を固定し、独立・盲検の複数ラベル、意見不一致の裁定、保留集合、経路版、全入力digestを一つの再生可能な束へ結合する。

この契約が返す `established_for_declared_population` は、宣言された評価方針を束内の標本が満たしたという限定状態である。semantic-guard全体の実務妥当性、修復効果、現場での人間利用、運用適格性、導入可否、又は人間の最終受理を意味しない。

## 原点目的との接続

| 原点 | この試作が担うもの | 担わないもの |
|---|---|---|
| `OR-01` | 直接規則、形態素解析、係り受け解析、LLMという候補経路を、要求工学上の同一監査命題・同一標本で比較する | 監査命題又は工学規則そのものの正しさ・完全性 |
| `OR-02` | case、subject、population、label guide、label、holdout、run、policyをdigestで結合し、どの条件でどの結果が出たかを限定的に再生する | 時刻・本人性・独立性・原資料真正性・因果性の暗号学的又は外部的証明 |
| `OR-03` | 費用、閾値、最低標本数、方針採択、導入、人間受理をsemantic-guardの権限外へ置く | semantic-guard自身による費用決定、方針採択、切替、最終受理 |

## 評価順序と比較単位

比較順は次で固定する。

```text
direct_only → morphology → dependency → llm
```

各経路は同一の `case_set_digest` を持ち、全caseを一度ずつ予測しなければならない。従って「LLMだけ難しい事例を除外する」「形態素解析だけ別母集団を使う」「欠測をなかったことにする」という比較は成立しない。

`incremental_values` は隣接する三組について次を決定論的に返す。

- 費用加重損失の減少量
- 被覆率の差
- 偽充足率・偽反証率の差
- 前段の棄権を正解へ解消した件数
- 前段の正解又は棄権から新たに誤りへ移した件数

これは各経路を累積構成として実装したこと自体を証明しない。`route_config` の版とdigestを外部構成記録へ結び、経路名と実装内容の一致を別途検査する必要がある。

## 人間所有の評価方針

方針は少なくとも次を持つ。

- `pending` / `adopted` / `retired`
- 対象母集団、用途、分析単位、標本枠、包含・除外条件
- 必須層と各層の定義
- 偽充足、偽反証、棄権の相対費用
- 偽充足が破局的誤りであるという明示
- 五つの通過閾値
- 全体、正例、反例、必須層ごとの最低標本数
- 信頼水準、主評価量、候補経路、証拠種別、再査読条件
- 方針版と内容digest

`adopted` 又は `retired` は、方針ID・版・digestへ一致する外部人間判断記録を必須とする。採択は保留集合の封印より前でなければならない。これは結果を見た後で費用又は閾値を都合よく決めることを防ぐためである。

semantic-guardは方針から結果を計算し、結合と整合を検査するだけである。費用、閾値、最低標本数、主評価量、導入判断を選ばない。

## ラベルと保留集合

各caseは、不変な `subject_digest`、母集団、用途、層、出所種別を持つ。全caseは保留集合へ封印され、ラベル公開前に四経路の予測が記録されなければならない。

各caseには最低二人のラベルが必要であり、実際にそのcaseを担当した査読者が、互いに異なる独立集団に属し、経路出力と他者ラベルの双方に対して盲検でなければfield validityは成立しない。独立査読者が名簿にいるだけでは足りない。

ラベルは保留集合の封印後、公開時刻以前に記録する。複数ラベルが一致しないcaseは、全基礎ラベルを引用する別の裁定記録を必須とする。ラベル指針はID、版、digestで固定する。

各runについて次を拒否する。

- 保留caseを学習・調整へ利用した記録
- ラベル参照禁止が偽であるrun
- 保留集合封印前又はラベル公開以後の予測
- 母集団、方針、保留集合、ラベル束、case集合の結合不一致
- case欠落、余分なcase、重複case、case digest差替え

ただし、現段階の時刻、盲検、独立性は束内の申告であり、署名済み外部台帳による事実証明ではない。

## 評価量

経路ごと、及び全層ごとに次を計算する。

| 評価量 | 分子 | 分母 |
|---|---|---|
| 偽充足率 | 正解が `refuted` なのに `satisfied` とした件数 | 正解が `refuted` の件数 |
| 偽反証率 | 正解が `satisfied` なのに `refuted` とした件数 | 正解が `satisfied` の件数 |
| 棄権率 | `abstain` 件数 | 全件数 |
| 被覆率 | 非棄権件数 | 全件数 |

各率には、人間方針の信頼水準を用いた両側Wilson score intervalを併記する。分母がゼロなら点推定値と区間端は `null` であり、閾値を通過しない。

費用加重損失は次である。

```text
(偽充足件数 × 偽充足費用
 + 偽反証件数 × 偽反証費用
 + 棄権件数 × 棄権費用) / 全件数
```

現行v0の閾値判定は、偽充足率・偽反証率・棄権率にはWilson上限、被覆率にはWilson下限を用いる。従って、点推定が誤率0又は被覆率1でも、標本数が乏しく信頼限界が閾値を越える時は通過しない。`threshold_assessment.criteria` は点推定、実際の比較値、比較根拠、信頼水準を分離して保存する。

費用加重損失は複数種類の誤り費用を合成した量であり、現行では点推定を使う。その比較根拠も `point_estimate` として露出する。費用損失の標本不確実性をどう評価するかは、母集団と費用模型に応じた別の統計方針を要し、人間所有の未決定事項に残す。

## Field validityの閉鎖条件

次のいずれか一つでも該当すれば `not_established` になる。

- 方針が `adopted` でない
- 採択記録が方針のID・版・digestへ一致しない
- 方針採択が保留集合封印より後である
- 独立査読者が二集団未満、又は実際の各caseに二つの独立集団が参加していない
- 査読者又はラベルの盲検が成立しない
- 全体、正例、反例、必須層の最低標本数を満たさない
- 候補経路がいずれかの閾値を満たさない
- 方針又はcaseが `local_fixture` / `smoke` である

構造破壊、digest不一致、欠測、重複、保留汚染、裁定欠落は「低い妥当性」として受理せず、bundle検証自体を失敗させる。保存済み `metrics` と `field_validity` は常に入力から再計算し、書き換えを拒否する。

## 別軸として未評価に保つもの

四経路の検出比較から、次を推定してはならない。

- `repair_effect`: 指摘後の修正が実際に成功したか
- `human_operational_use`: 人間が理解・判断でき、負荷と誤用が許容範囲か
- `operational_qualification`: 安全性、信頼性、容量、事故対応、導入運用が適格か

これらは常に `not_evaluated` として別欄へ保存する。検出成績をもって修復成功、業務価値、導入準備完了へ昇格させない。

## 純粋API

```python
from semantic_guard.field_evaluation import (
    build_evaluation_policy,
    build_human_policy_decision,
    build_field_case,
    build_blind_label,
    build_adjudication,
    build_field_evaluation,
    validate_field_evaluation,
)
```

- builder群は入力を正規化し、SHA-256でcontent-addressedな束を作る。
- `field_evaluation_errors` は閉鎖的な失敗を安定したerror codeで返す。
- `validate_field_evaluation` はschema、全digest、全参照、保留隔離、同一case比較、評価量、妥当性状態を再生し、外部書込みを行わない。

## 検証

```sh
uv run --locked python -m unittest tests.test_field_evaluation -v
```

試験は、決定論的な四経路比較、Wilson区間、増分価値、独立盲検ラベル、裁定、pending方針、最低標本不足、閾値失敗、fixture非一般化、case・母集団・label・run・費用・閾値の差替え、重複、保留汚染、別case集合を使うLLM、偽の妥当性昇格を反証する。

試験中の肯定経路はschemaと計算の単体試験用人工データであり、semantic-guardの実在母集団におけるfield validity証拠ではない。

## 現在の限界と次の実務作業

- 内部schema・builder・validatorだけであり、CLI、MCP、既存audit contract、永続台帳へ未接続である。
- 実在の母集団定義、標本抽出、事前登録、標本数設計、独立査読者、裁定者、実測runがまだない。
- 方針採択、査読者本人性、独立性、盲検、時刻、run実行は自己申告値であり、署名、外部観測、append-only ledgerを要する。
- `route_config` のdigestは経路構成参照を固定するが、実行binary、辞書、形態素解析器、係り受け解析器、prompt、model receiptとの実結合は未実装である。
- 率の閾値はWilson信頼限界で保守的に判定するが、費用加重損失は点推定のままであり、その不確実性評価方針は未決定である。
- 層別評価は件数と率を出すが、交互作用、領域移動、時系列劣化、公平性、校正、標本抽出偏りは評価しない。
- label guideの内容妥当性、監査命題の完全性、工学rule-packの採択妥当性は別の査読・評価を要する。
- 修復効果、人間運用、運用適格性は別研究設計と別証拠束が必要である。

従って、v0が可能にしたのは「何を同じ条件で比べ、どこでfield validityを止めるか」の機械検査である。現在のsemantic-guardが実務領域で有効だという証明は、まだ一件も作っていない。
